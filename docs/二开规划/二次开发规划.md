# 基于 Superpowers Fork 的二次开发规划

> 适用场景：已 fork `obra/superpowers`，团队 harness 为 Codex / Cursor / Claude Code。
> 思路：**阶段一只做"机器可见命名与引用迁移"，确保与官方版可独立启停且单装时行为等价；阶段二只解决团队对官方默认行为不认可的三处痛点：触发太频繁、产物路径不合适、缺少长期规格库。其它一切"看上去更严谨"的设计（状态机、acceptance evidence 严格分类、事务化归档、conversation sha256、PR 在线核验、统一 `t-validate` 校验器、subagent 强制模板等）一律不做。**

---

## 1. 一句话结论

```text
阶段一不引入任何新入口（new skill），把 14 个 skill、4 处必改 manifest 的 name、
运行时引用、hook 内机器可见 skill 标识，加上 t- 前缀整体迁移，让 fork 成为一个
独立的、可与官方插件同时安装的 "t-superpowers" 插件。阶段一已完成（见
"docs/二开规划/阶段一验收记录.md"）。

阶段二只做三件事，对应团队对官方默认行为不认可的三处痛点：

1. 触发太频繁 → 双通道收敛：t-using-superpowers 弹性化 + 关键 SKILL
   frontmatter description 收敛。明确不采用 allow_implicit_invocation: false。
2. 产物路径不合适 → 把 t-brainstorming / t-writing-plans 的产物路径从
   docs/superpowers/{specs,plans}/ 切换到 docsDev/changes/<change-id>/。
3. 缺少长期规格库 → 在 docsDev/specs/<capability>/spec.md 建立长期共享
   规格库；新增 t-archive skill 作为轻量壳，由用户显式触发，内部调用
   tools/t-archive-precheck + 合并 Archive Patch + git mv + git commit
   三步；失败用 git reset 兜底，不做事务化备份与 sha256。

阶段二不引入：
  - 状态机（draft/ready/running/implemented/blocked/verified/accepted/archived）
  - plan.md frontmatter 上的 status / status_history / blocked_reason /
    unblocked_reason / acceptance_evidence / pending_acceptance_evidence /
    archive_failure 等字段
  - acceptance evidence 三类严格分类、conversation sha256、PR 在线核验
  - 事务化归档（backup + atomic rename + 按步骤分类回滚）
  - 统一的 tools/t-validate / tools/t-state 大型校验器
  - 强制的 subagent dispatch prompt 模板

阶段二允许引入：
  - 新增 1 个 skill 入口：t-archive（仅做归档流程包装，不引入事务化）
  - tools/t-archive-precheck（≤ 100 行的小脚本，做归档前的路径越界 / 幂等
    / working tree 干净三项检查；被 t-archive skill 调用）
  - 若干 PR 阶段的 CI lint（grep 路径泄漏、grep superpowers:<x> 残留等）

t-archive skill 由用户显式触发（"归档这个 change" / "走 t-archive"），
不得在 verification 完成后自动接管。
```

## 2. 真实诉求

### 2.1 认可 Superpowers 的部分

认可的是 Superpowers 的"底层工程纪律"：

- `brainstorming`：先理解上下文、澄清需求、比较方案、明确 trade-off。
- `writing-plans`：把需求变成可执行、可验证、细粒度的实施计划。
- `test-driven-development`：复杂行为变更和 bugfix 采用红绿重构。
- `systematic-debugging`：复杂 bug 先复现、定位根因、验证假设。
- `verification-before-completion`：完成声明必须有新鲜验证证据。
- `subagent-driven-development`：fresh subagent 分任务执行 + 两轮 review。
- `using-git-worktrees` / `requesting-code-review` / `receiving-code-review` / `finishing-a-development-branch`。
- `writing-skills`：把 skill 本身按 TDD 思路迭代。

这些纪律靠 prompt + skill 自身约束就能落地，**不需要确定性校验器**。Superpowers 上游也是这么做的。

### 2.2 不认可 Superpowers 默认行为的部分（阶段二只解决这三件事）

- **触发太频繁**：通过 `hooks/session-start` 强制注入 `using-superpowers` 全文，倾向"只要像开发任务就自动介入"；同时各 skill SKILL frontmatter 的 `description` 也会让 Codex 隐式触发 brainstorming 等 skill。
- **产物路径不合适**：默认写 `docs/superpowers/specs/...` 和 `docs/superpowers/plans/...`（来自 `skills/brainstorming/SKILL.md`、`skills/writing-plans/SKILL.md`），希望统一到 `docsDev/`。
- **缺少长期规格库**：复杂需求完成后没有沉淀到团队共享规格库的固定路径。

### 2.3 目标用户与使用方式

- 团队规模：约 10 人小开发团队，使用 Codex / Cursor / Claude Code。
- 简单需求：使用 Agent 普通模式或 Agent Plan Mode。
- 复杂需求：使用 fork 的 `t-superpowers` 插件，进入 `t-*` skill 链路。
- 目标：复杂需求质量更高，规格沉淀，且不与官方 superpowers 命名冲突。

> 10 人内部团队的信任成本远低于跨组织协作。团队完全可以靠 PR review + 显式人工验收推进，不需要为"acceptance 是否被伪造"这种问题构建密码学级别的校验。

### 4.5 vendor 基线机制

`vendor/superpowers/UPSTREAM_COMMIT` 文件，每次 vendor 同步必须更新：

```text
upstream: https://github.com/obra/superpowers
branch: main
commit: <full-sha>
synced_at: 2026-05-08T09:00:00Z
notes: <可选说明>
```

要求：

- `commit` 字段必须是 7 位以上十六进制，不允许空。
- vendor 同步必须从该 commit 对应的 upstream 树**完整拉取**（含 skills/、hooks/、CLAUDE.md、AGENTS.md、GEMINI.md、各 manifest），不能只同步 skills/。
- `tools/t-stage1-check.sh` 会校验文件存在与 commit 字段格式。

## 6. 阶段二：解决三处痛点（每条独立可上线）

阶段二只做三件事 + 一处 harness 元数据收敛 + 一个轻量校验脚本。**任何超出这五节范围的"看起来更严谨"设计都不做。**

### 6.1 痛点 #1：触发面收敛（双通道）

阶段一保留了原版 `using-superpowers` 的 1% skill-first 强约束。阶段二必须**双通道**收敛。

#### 通道 1：t-using-superpowers 弹性化

修改 `skills/t-using-superpowers/SKILL.md`：

```text
原版（保留在 vendor/superpowers/skills/using-superpowers/）：
  "如果有 1% 可能某个 skill 适用，就必须先调用 skill"

t-using-superpowers 弹性版本：
  "明显属于复杂需求（多文件改动、行为变更、bugfix、需求澄清缺失等）时，
   必须使用对应 t-* skill；
   明显属于简单请求（小文案、小样式、问答、调研）时，
   按 harness 默认行为处理，不强制 skill。"
```

#### 通道 2：关键 t-* SKILL frontmatter description 收敛

Codex 的隐式触发依赖 `description`。即使 t-using-superpowers 已经弹性化，Codex 仍可能根据 `t-brainstorming.description` 直接触发 brainstorming。阶段二必须同步收敛 description：

```yaml
# 旧 description（upstream 原文）：
description: Use this before any creative work - creating features,
  building components, adding functionality, or modifying behavior.

# 新 description（收敛版，强调"复杂"边界）：
description: Use ONLY for complex multi-file features, behavior changes,
  or requirements that need clarification before implementation.
  Do NOT use for single-file edits, copy/style/config tweaks, Q&A, or
  pure code reading. The user must signal complexity (or you must verify
  it spans multiple files / introduces new behavior).
```

需要同步收敛 description 的关键 skill：`t-brainstorming`、`t-writing-plans`、`t-test-driven-development`、`t-systematic-debugging`、`t-subagent-driven-development`。

#### 判定指引（写入 t-using-superpowers）

| 场景 | 是否强制 t- skill | 备选 |
| --- | --- | --- |
| 用户明确说"用 t-superpowers" / "走 brainstorming" | 强制 | 直接进入对应 skill |
| 多文件改动 / 行为变更 / 新功能 | 强制 | 至少 t-brainstorming → t-writing-plans |
| 复杂 bugfix（首次出现、根因不明） | 强制 | t-systematic-debugging |
| 单文件文案 / 样式 / 配置改动 | 不强制 | 直接处理 |
| 纯问答 / 纯代码阅读 / 纯调研 | 不强制 | 直接回答 |
| 模糊场景 | **拒绝自动介入**，提示用户显式声明 | "这看起来比较复杂，要走 t-superpowers 完整流程吗？" |

#### 明确不采用 `policy.allow_implicit_invocation: false`

会同时禁掉"复杂需求的自动触发"，违反 §2.3 中"复杂需求自动走 t-* 流程"的诉求；我们想要"简单不触发、复杂触发"的弹性边界，只能通过 description 的语义收敛实现。

### 6.2 痛点 #2：产物路径统一到 docsDev/

修改对象：`t-brainstorming/SKILL.md`、`t-writing-plans/SKILL.md`、以及任何引用旧路径的 references。

```text
docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md
  → docsDev/changes/<change-id>/spec.md

docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md
  → docsDev/changes/<change-id>/plan.md
```

新增长期规格库与归档根（§6.3）：

```text
docsDev/specs/<capability>/spec.md      # 团队长期共享规格库
docsDev/archive/<change-id>/            # 归档后的 change 完整快照
```

#### change-id 命名规范（统一 UTC）

```text
格式：YYYYMMDD-<slug>
  - YYYYMMDD：UTC 日期，由 t-brainstorming 在创建目录时通过
              `date -u +%Y%m%d` 生成；不允许使用本地日期
  - slug：a-z0-9- 组成，长度 3-40 字符
  - 示例：20260508-add-billing-export
```

时间字段约定：

- frontmatter 中所有日期字段（如 `created_at` / `updated_at`）使用 ISO 8601 UTC（如 `2026-05-08T03:21:00Z`）。
- 团队若希望改用本地时区，必须由一次独立变更全篇统一切换，不接受局部混用。

#### change-id 冲突规则

- `t-brainstorming` 创建目录时，目录已存在直接报错并提示用户换 slug。
- `tools/t-archive-precheck`（§6.5）在归档前检查目标 `docsDev/archive/<change-id>/` 不存在。

> **不引入**任何形式的状态机、status_history、blocked_reason、acceptance_evidence、archive_failure 等字段。plan.md frontmatter 只放最小必要信息：`change_id`、`created_at`、`updated_at`、`owner`。

### 6.3 痛点 #3：长期规格库 + t-archive skill（阶段二唯一新增 skill）

#### 长期规格库

确立 `docsDev/specs/<capability>/spec.md` 为团队长期共享规格库。

模板：

```markdown
---
capability:
owner:
updated_at:
source: t-superpowers
---

# <Capability> Spec

## Change History
- YYYY-MM-DD: archived from docsDev/changes/<change-id>/ (<short summary>)

## Overview

## Requirements

### Requirement: <行为名称>
系统必须 ...
#### Scenario: <场景名称>
- Given ...
- When ...
- Then ...

## Notes
```

> Change History 块放在 frontmatter 之后、Overview 之前，每次归档 append 一条。

#### Archive Patch（写在 change 的 spec.md 末尾，归档时合入 long-term spec）

```markdown
## Archive Patch

### <capability>

Target: docsDev/specs/<capability>/spec.md
Action: create | update

#### ADDED Requirements
##### Requirement: <新增行为名称>
系统必须 ...
###### Scenario: <场景名称>
- Given ...
- When ...
- Then ...

#### MODIFIED Requirements
##### Requirement: <已有行为名称>
Replace with:
系统必须 ...
###### Scenario: <场景名称>
- Given ...
- When ...
- Then ...

#### REMOVED Requirements
- Requirement: <要删除的行为名称>
- Reason: <删除原因>

#### RENAMED Requirements
- From: <旧名称>
- To: <新名称>
- Reason: <重命名原因>
```

#### t-archive skill（轻量壳，不引入事务化）

归档由 `t-archive` skill 包装，**由用户显式触发**，内部按下面五步执行，全部落到一个 git commit 内。任一步失败即停止、不重试、由 git reset 兜底。

```text
用户：归档 <change-id>     # 或 "走 t-archive" / "把 <change-id> 沉淀到 specs"
t-archive skill：
  1. 调用 tools/t-archive-precheck <change-id>（详见 §6.5）
     失败 → 报告原因（含退出码语义），停止
  2. 解析 docsDev/changes/<change-id>/spec.md 末尾的 Archive Patch 块
     拿到 Target / Action / ADDED / MODIFIED / REMOVED / RENAMED 列表
  3. 把 Archive Patch 合并到 docsDev/specs/<capability>/spec.md：
     - Action=create 时：用 §6.3 长期规格库模板新建文件
     - Action=update 时：在文件内插入 ADDED Requirement、替换 MODIFIED
       Requirement、删除 REMOVED Requirement、重命名 RENAMED Requirement
     - 在 long-term spec 的 Change History 顶部 append 一条
       "<YYYY-MM-DD>: archived from docsDev/changes/<change-id>/ (<summary>)"
  4. git mv docsDev/changes/<change-id> docsDev/archive/<change-id>
  5. git add docsDev/specs docsDev/archive
     git commit -m "archive <change-id>: <summary>"
  → 报告 commit sha + 摘要
```

#### 触发边界（写入 t-archive SKILL frontmatter description）

```yaml
description: Use ONLY when the user explicitly asks to archive a specific
  change-id into docsDev/specs/ (e.g. "archive 20260508-add-billing-export",
  "走 t-archive", "把这个 change 沉淀到 specs"). Do NOT auto-trigger after
  t-verification-before-completion succeeds. Do NOT infer archive intent
  from phrases like "looks good" / "ok" / "可以了". The user must name an
  explicit archive intent and a change-id.
```

> t-archive **不进入** t-using-superpowers 的"自动复杂需求链路"。即使一个 change 已经完成 verification，agent 也不得自动调用 t-archive——必须等用户明确说"归档"。

#### 失败兜底

| 失败位置 | 处理 |
| --- | --- |
| 第 1 步 precheck 退出非零 | 报告 precheck 输出（含越界路径 / 幂等冲突 / 工作区脏等具体原因），不动任何文件 |
| 第 2 步 Archive Patch 解析失败 | 报告字段缺失位置，不动任何文件 |
| 第 3 步合并到 long-term spec 出错 | `git reset --hard HEAD && git clean -fd`（precheck 已确认起点干净，回到归档前状态） |
| 第 4 步 git mv 失败 | 同上 |
| 第 5 步 commit 前发现内容错 | 同上 |
| 第 5 步 commit 之后发现错 | 用户决定 `git revert <archive-commit>` 或新 commit 修正；skill 不自动重试 |

#### 明确不做（保留过度设计禁令）

- 不做事务化备份目录（`docsDev/archive/<id>.tmp/`）+ checksum + atomic rename + 按步骤分类回滚表。
- 不写 `archive_failure` frontmatter 块；不保留 "原 change status 保持 accepted" 等状态语义（本来就没有 status 字段）。
- 失败后不自动重试、不破坏性清理。
- 不做并发 sha256 校验（precheck 第 5 项工作区干净 + git mv 在单 commit 内已经足够）。

#### 为什么这么做

- skill 包装解决了"用户记不住 3 条命令、不想手动 merge markdown"的真实体验问题——这是用户 2026-05-11 反馈的核心诉求。
- skill 内部仍然轻量：只调一个 ≤ 100 行的 precheck 脚本 + 几个 git 命令 + Markdown merge，没有事务化复杂度。
- git 已经天然提供：原子提交（commit 是一个原子点）、完整历史（archive commit 可 revert）、回滚兜底（reset --hard）。再加一层备份只是在用户和 git 之间塞了一层不必要的间接。

#### plan.md 演进策略

- `spec.md`：允许 rewrite 正文，建议在顶部维护 `## Change History` 块，每次重写 append 一条原因（不强制 CI 检查）。
- `plan.md`：正文任务区只允许 append，任务被废弃时不要删除，改为标记 `[ABANDONED]` 并写原因，保留任务 id；执行日志、verification log、discoveries 都是 append。
- **不引入** "frontmatter 仅由 validator 写入" 的强约束。frontmatter 是人和 agent 都可读可写的简单元数据。

### 6.4 三个 harness 各自的元数据收敛

| Harness | 收敛动作 |
| --- | --- |
| Cursor | `.cursor-plugin/plugin.json` 的 `description` 改为"复杂需求才介入"语义 |
| Claude Code | `.claude-plugin/plugin.json` 的 `description` 同上；`hooks/session-start` 注入正文中的品牌串与 EXTREMELY_IMPORTANT 段语义可在此阶段调整 |
| Codex CLI / App | `.codex-plugin/plugin.json` 的 `interface.longDescription` 改写；`defaultPrompt` 默认 `I've got an idea for something I'd like to build.` 会诱导自动 brainstorming，需收敛为 `Let me describe a complex change I want to plan with t-superpowers.` 之类显式语义 |

阶段二验证：在每个 harness 上跑一遍"小文案"输入，确认不自动进入 t-brainstorming（详见 §6.6）。

### 6.5 轻量校验工具 `tools/t-archive-precheck`

实现要求：

- 单文件脚本（Python 或 Bash），≤ 100 行。
- **不依赖** LLM、不调用网络、不解析 transcript。
- 被 `t-archive` skill 在归档第 1 步调用；也允许人工直接调用做"预演检查"。
- 只做下列检查，任一失败即非零退出：

```text
1. 参数 <change-id> 必填，目录 docsDev/changes/<change-id>/ 存在
2. spec.md 末尾含 "## Archive Patch" 块，且每个子节有 Target/Action 与
   至少一个 Requirement + Scenario
3. 每个 Archive Patch Target 通过路径规范化检查：
   - 解析为绝对路径（含 symlink resolve）
   - 必须严格位于仓库根的 docsDev/specs/ 之内
   - 不允许 target 等于 docsDev/specs/ 根
4. docsDev/archive/<change-id>/ 不存在
5. git status --porcelain 输出为空（含 untracked）
```

退出码：

```text
0   全部通过
1   参数或目录缺失
2   Archive Patch 字段缺失或格式错误
3   Target 路径越界
4   幂等冲突（archive 目录已存在）
5   工作区不干净
```

> 这是阶段二**唯一**新增的工具。不会扩展为统一 `t-validate` 入口，也不会增加 state-transition / acceptance 子命令。退出码语义供 `t-archive` skill 在失败时如实转述给用户。

### 6.6 验证清单（每条独立可跑）

每条用例三段式：transcript 期望出现 + transcript 不应出现 + 文件状态断言。**只覆盖三处痛点直接相关的场景**，不再有 17 个用例。

| 场景 | 输入 prompt | 期望出现 | 不应出现 | 文件状态断言 |
| --- | --- | --- | --- | --- |
| 误触发拦截（bootstrap 通道） | "帮我把按钮文案从'确定'改成'OK'" | "这是简单文案修改，按你当前请求直接处理" | "进入 t-brainstorming"、"docsDev/changes" | `docsDev/changes/` 无新建子目录 |
| 误触发拦截（Codex description 通道） | 在 Codex CLI 直接喂"帮我加一个 README 段落" | Codex 不隐式跳到 t-brainstorming；普通文本编辑响应 | `t-brainstorming` 出现在 transcript skill stack | `docsDev/` 无新增 |
| 显式触发 + spec | "用 t-superpowers，我要做一个 PDF 导出功能" | "已创建 docsDev/changes/<change-id>/spec.md" | "docs/superpowers/specs" | `docsDev/changes/<change-id>/spec.md` 存在；`docs/superpowers/` 无新写入 |
| 路径泄漏回归 | 执行任意 t-brainstorming / t-writing-plans 链路 | spec/plan 写入 docsDev/changes/ | "docs/superpowers/specs"、"docs/superpowers/plans" | `docs/superpowers/` 无新增；`docsDev/changes/` 有对应文件 |
| t-archive 自动触发拦截 | change 完成 verification 后，agent 继续往下做事，但用户没有说"归档" | agent 不调用 t-archive；不生成 archive commit | "进入 t-archive"、"已归档" | `docsDev/archive/` 无新增；无 archive commit |
| t-archive 显式触发 + precheck 路径越界 | 用户："归档 <change-id>"；spec.md 的 Archive Patch Target 写 `docsDev/specs/../etc/x.md` 或 `docs/superpowers/foo/spec.md` | t-archive 报告 "precheck 退出码 3：路径越界" | "归档完成"、`git commit` 被触发 | 无任何文件被修改 |
| t-archive 显式触发 + 幂等 | 同一 change 第二次执行 t-archive | t-archive 报告 "precheck 退出码 4：archive 目录已存在" | "归档完成" | 无任何文件被修改 |
| t-archive 显式触发 + 工作区脏 | 用户："归档 <change-id>"，但当前 working tree 有未提交改动 | t-archive 报告 "precheck 退出码 5：工作区不干净"，提示用户先 commit/stash | "归档完成"、自动 stash | 无任何文件被修改 |
| t-archive 合法归档 | precheck 通过 + Archive Patch 合并 + git mv + commit | t-archive 报告 commit sha 与摘要 | "失败"、"拒绝" | `docsDev/specs/<capability>/spec.md` 含 ADDED/MODIFIED 内容；`docsDev/archive/<change-id>/` 存在；`docsDev/changes/<change-id>/` 不存在；`git log` 出现 archive commit |

判定：每个用例必须语义匹配"期望出现"、不出现"不应出现"、且文件状态断言全部通过。

> 不再做：状态转移压力用例、blocked-no-reason、conversation-evidence-fake、archive-concurrent-modify、archive-fail-recovery 等。这些场景对应的设计本身已经被砍掉。

## 7. 长期维护节奏（fork 与 upstream 同步）

### 7.1 rebase 节奏

- 每月固定一次 upstream rebase（每月第 1 个工作日）。
- upstream 发布 release 时（看 `RELEASE-NOTES.md`）触发额外评估。
- 安全/缺陷紧急修复 48 小时内拉取。

### 7.2 rebase 流程

```text
1. git fetch upstream && git merge / rebase upstream/main 到 fork dev 分支
2. 同步 vendor 与基线（完整范围）：
   - 用 upstream 最新版本覆盖 vendor/superpowers/{skills/, hooks/, CLAUDE.md,
     AGENTS.md, GEMINI.md, *.plugin/plugin.json, .claude-plugin/marketplace.json,
     package.json, gemini-extension.json}
   - 更新 vendor/superpowers/UPSTREAM_COMMIT 的 commit / synced_at / notes
   - 用 vendor/superpowers/CLAUDE.md 重新生成 docs/upstream-contrib.md
3. 对每个有改动的 upstream skill：
   diff vendor/<old> vs vendor/<new>
   决定是否需要把同样改动应用到 skills/t-<name>/
   - 特别注意：t-using-superpowers、t-brainstorming、t-writing-plans 已在
     阶段二做了行为/路径修改，rebase 时手动 reconcile，不要被 upstream
     文本机械覆盖
4. 对 hooks/session-start：检查 upstream 是否调整注入正文；若调整，
   同步行为塑造改动到 fork（注意保留运行时 skill 标识为 t-* 形式）
5. 检查 upstream 是否对 3 处明确排除入口有改动；只更新 vendor/ 副本，
   不改根文件
6. 跑 tools/t-stage1-check.sh + §6.6 验证清单
7. 通过后合并发布
```

### 7.3 变更评估清单

每次 rebase 前对照 upstream `git log`：

- upstream 是否新增 skill？→ 默认不引入，由团队决议是否新增 `t-<name>`。
- upstream 是否修改 `using-superpowers` 行为？→ 高风险，必须人工确认是否影响 t-using-superpowers 的弹性化逻辑。
- upstream 是否改 `hooks/session-start`？→ 高风险，diff 后再合入。
- upstream 是否改 4 处必改 manifest 字段格式？→ 同步对应 fork 文件的字段结构（不改 name）。
- upstream 是否改 3 处明确排除入口？→ 仅同步到 vendor/，根文件不动。
- upstream 是否改 CLAUDE.md / AGENTS.md / GEMINI.md？→ 仅同步到 vendor/ 与 docs/upstream-contrib.md。
- upstream Codex 插件文档/schema 是否更新？→ 检查 hooks 字段语义、SessionStart 用法、隐式调用规则。

## 8. 必须避免的坑

### 8.1 不要回退到"看起来更严谨"的过度设计

阶段二刻意舍弃了以下设计，**任何 PR 都不应该把它们以"完善"为理由重新加回来**：

- 状态机（draft → ready → running → … → archived）
- plan.md frontmatter 上的 status / status_history / 各种 reason 字段
- acceptance evidence 三类严格分类（conversation / pr / ticket）
- conversation 类 sha256 + transcript 路径核验
- PR 在线核验（GET API 拿 review state）
- 事务化归档（backup + atomic rename + 按步骤分类回滚表）
- 统一 `tools/t-validate` 大型校验器
- 强制 subagent dispatch prompt 模板

如果有人想加回任一项，应先回答：**它解决的具体问题在过去 3 个月内的 changes 里出现过几次？** 如果答案是零，就不加。

### 8.2 阶段一已迁移项不要回退

- 4 处必改 manifest 的 `name` 必须保持 `t-superpowers`（marketplace 为 `t-superpowers-dev`）。
- 3 处明确排除入口（`package.json` / `gemini-extension.json` / `.opencode/plugins/superpowers.js`）保持原 `name = superpowers`，字节级不改。
- 跨 skill 与 hook 内的运行时引用必须保持 `t-superpowers:t-<x>` 形式。
- `hooks/session-start` 不得引用 `skills/using-superpowers/` 或 `superpowers:using-superpowers`。

### 8.3 不要把"co-installed"当作"行为等价"

同时安装官方与 fork 会双重 SessionStart 注入，行为本就不会等价。三类测试（official-only / fork-only / co-installed）语义不能混。

### 8.4 不要让 archive precheck 路径校验只查前缀

`Target: docsDev/specs/../etc/x.md` 仅查前缀会通过。必须做 normalize + symlink 解析 + `relative_to` 子树校验，且禁止 target 等于 specs 根（§6.5）。

### 8.5 不要在 working tree 脏的情况下执行归档

归档约定的所有"失败就 git reset"兜底，前提是 precheck 通过时工作区是干净的。如果绕过 precheck，git reset 会丢用户未提交改动——这是 §6.5 第 5 项检查的意义。

### 8.6 t-archive 必须由用户显式触发

虽然我们不做严格的 acceptance evidence 校验，但归档必须由用户在 PR 或对话中**显式发起**："归档 <change-id>" / "走 t-archive" / "把这个 change 沉淀到 specs" 等。

**禁止的自动触发模式**：

- t-verification-before-completion 通过 → 自动调用 t-archive。
- 用户说"看起来 ok 了" / "没问题" / "可以" → 自动调用 t-archive。
- 在 t-using-superpowers 的"复杂需求自动链路"中把 t-archive 串进去。

t-archive 的 SKILL frontmatter description 必须明确写出这条边界（§6.3）。

### 8.7 不要直接修改 upstream 副本

`vendor/superpowers/` 是只读参考，rebase 自动覆盖。任何对它的本地改动都会在下次 rebase 时丢失。

### 8.8 不要一次性大批量修改所有 skill

阶段二三件事（触发收敛 / 路径迁移 / 长期规格库）独立完成、独立验证、独立上线。一次 PR 只动一件。
